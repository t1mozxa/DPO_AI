# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался предоставленный датасет `S12-hw-dataset.csv` с часовыми данными временного ряда.
- Выполнен корректный `train / validation / test` разбор по времени без перемешивания.
- Сравнивались 4 подхода: `naive-last`, `moving-average`, `ridge-lag-features`, `gru-forecast`.
- Лучшей оказалась модель `gru-forecast`, которая показала наилучшие результаты по MAE на тесте.

## 2. Среда и воспроизводимость

- Python: 3.11+
- pandas / numpy / scikit-learn: последние стабильные версии
- torch: 1.9.0+
- Устройство (CPU/GPU): GPU (если доступен), иначе CPU
- Seed: 42
- Как запустить: открыть `HW12.ipynb` и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: часовая
- Горизонт прогноза: 1 шаг (следующий час)
- Размер датасета: 4392 наблюдения
- Диапазон дат: с 2025-01-01 по 2025-06-29
- Есть ли дополнительные внешние признаки: нет, только целевая переменная
- Комментарий (2-4 предложения): Ряд демонстрирует выраженную суточную сезонность, умеренный тренд и некоторые выбросы. Данные содержат часовую информацию, что позволяет строить признаки на основе времени суток. Визуально ряд стационарен в пределах наблюдений, что делает его подходящим для прогнозирования.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: 70% / 15% / 15% по хронологическому порядку
- Какие доли или интервалы использовались: 3064 / 659 / 669 наблюдений соответственно
- Почему `random split` здесь некорректен: потому что перемешивание нарушает хронологический порядок и приводит к утечке информации из будущего в прошлое, что делает оценку качества нереалистичной.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7`
- Какие календарные признаки использовались: `hour`, `day_of_week`, `day_of_month`, `month`, `hour_sin`, `hour_cos`, `dow_sin`, `dow_cos`
- Как обрабатывались пропуски после построения лагов/rolling: удаление строк с пропусками
- Использовалось ли масштабирование и где именно оно обучалось: StandardScaler обучался на train, применен ко всем частям

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): Наивная модель, прогноз равен последнему известному значению
- B2 (`moving-average`): Прогноз как среднее по последним 7 значениям
- B3 (`ridge-lag-features`): Ridge регрессия на лаговых и календарных признаках
- R1 (`gru-forecast`): GRU нейросеть с оконным представлением ряда

Дополнительно:

- Основная метрика выбора лучшей модели: `MAE` на validation
- Дополнительные метрики: `RMSE`, `MAPE`
- `window_size` для `GRU`: 24
- Batch size: 32
- Максимальное число эпох: 20
- Optimizer: Adam
- Learning rate: 0.001
- Как сохранялась лучшая модель: сохранение state_dict при минимальной validation ошибке

## 7. Анализ

Наивный baseline показал удовлетворительные результаты, но не смог уловить сложные паттерны в данных. Moving average дал небольшое улучшение по сравнению с наивным подходом, особенно в условиях шума. Ridge на лаговых признаках показала значительное улучшение, эффективно используя информацию из прошлого. GRU модель показала лучшие результаты, особенно на участках с нестандартной динамикой. Сезонность и тренд были хорошо уловлены всеми моделями, но GRU лучше справляется с неожиданными изменениями. Утечки данных могли бы возникнуть при неправильном масштабировании или использовании будущей информации в rolling окнах. Выбор по validation важен, чтобы избежать переобучения на test. Наиболее показательными ошибками стали участки с резкими изменениями, где все модели показали повышенную погрешность.

## 8. Итоговый вывод

Я взял GRU как базовый подход, так как она показала наилучшие результаты и лучше всего справляется с нелинейностями. Простой baseline на признаках хорошо использовать, когда данные стационарны и линейны. GRU стоит использовать, когда есть сложные нелинейные зависимости и сезонности. Корректная валидация по времени критична, чтобы избежать оптимистичной оценки качества.
